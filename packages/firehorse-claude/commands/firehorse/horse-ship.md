# Ship

## Purpose

Use this workflow after an issue-sized change has been accepted locally and is ready to become a pull request, merge, changelog entry, tag, and release. The workflow inventories the exact release scope, creates or updates the Pull Request, links solved issues accurately, runs validation and a reviewer gate, prefers squash merge for issue-sized slices, updates Keep a Changelog-style notes, decides the version bump with rationale, creates the tag/release when appropriate, and verifies linked issue and project status after merge.

## Usage

Invoke the generated provider command as `horse-ship` with an accepted issue URL, PR URL, branch name, release candidate summary, or explicit release scope. If `$ARGUMENTS` is missing or ambiguous, stop after inventory and ask for the release scope before creating or updating a PR, merging, tagging, or releasing.

## Inputs

- `$ARGUMENTS`: the accepted issue, PR, branch, release candidate, or release scope supplied by the user.
- The local git state, branch name, changed files, commits, generated artifacts, and validation evidence.
- Solved Published Issues, partially related issues, PR references, milestones, and project-board state.
- The applicable Verification Contract, acceptance criteria, previous reviewer findings, and any explicit merge or release policy.
- Existing changelog/release-note material such as `CHANGELOG.md`, package manifests, tags, and GitHub Releases.

## Outputs

- A release-scope inventory listing changed files, solved issues, partially related issues, unrelated local changes, release artifacts, validation evidence, and risks.
- A created or updated Pull Request with a body that uses `Closes #...` only for fully solved issues and `Refs #...` for partial, related, or follow-up issues.
- A review/validation gate result, including a canonical `reviewer` gate before merge unless explicitly skipped with rationale.
- Keep a Changelog-style notes updated for the shipped changes and release notes derived from those notes.
- A version bump decision such as major, minor, patch, prerelease, or explicit no-release, with rationale tied to the shipped changes.
- A merge, tag, and GitHub Release when the release checkpoint passes and credentials/policy allow it.
- Post-merge verification that linked issues are closed and Done where possible, reporting or repairing automation gaps with command evidence and any gaps that could not be repaired.

## Orchestration Intent

Keep shipping maintainer-led and evidence-driven. The workflow does not implement new product changes; it packages already accepted changes for review, merge, and release. First inventory the exact scope and separate unrelated dirty work, then create or update the PR, then run validation and reviewer gates, then update changelog and version material, then merge according to repository policy, then tag/release, and finally verify linked issue/project status. Provider-specific implementations may use `gh`, local release scripts, or review gates when available, but the canonical workflow remains a static shipping contract rather than a release bot or autonomous execution loop.

## Safety Gates

- Do not create/update a PR, merge, tag, or release until the changed files, solved issues, unrelated changes, and release scope are inventoried.
- Do not include unrelated dirty files in the PR or release. Either exclude them, preserve them for a separate slice, or stop for direction when they cannot be separated safely.
- Use `Closes #...` only when the shipped change fully solves that Published Issue. Use `Refs #...` for partial fixes, related context, dependencies, or follow-up work.
- Run or require a canonical `reviewer` gate before merge for non-trivial code, workflow, generated artifact, changelog, version, or release changes unless the user explicitly skips it; record the skip rationale and risk.
- Prefer squash merge for issue-sized slices unless repository convention, branch protection, or maintainer instruction requires merge commit, rebase merge, or manual merge.
- Do not invent validation, review, changelog, version, tag, release, or issue-status evidence. Record missing credentials or unavailable external systems honestly.
- Do not create tags or GitHub Releases from unmerged, unreviewed, or unvalidated changes unless the repository's documented release policy explicitly requires that flow.
- Do not add Firehorse setup-manifest validation, new-project setup, provider transports, prompt loaders, hooks, autonomous agents, or release automation beyond this static workflow definition.

## Procedure

1. Read `$ARGUMENTS` and identify the shipping target: accepted Published Issue, PR URL, branch, local release candidate, or explicit release scope.
2. Inventory the release candidate before PR creation or update: current branch, base branch, `git status --short`, changed files, generated artifacts, commits since base, solved issues, partially related issues, unrelated changes, validation evidence, changelog state, existing tags/releases, and release scope.
3. Stop or ask for direction when unrelated local changes cannot be safely separated. Otherwise state how unrelated changes will be excluded or preserved outside the PR/release.
4. Map issue links. Mark each Published Issue as fully solved, partially related, blocked, or follow-up. Plan PR body wording so fully solved issues use `Closes #...` and all other related issues use `Refs #...`.
5. Create or update the Pull Request with `gh` when GitHub access is available. Include summary, changed-file/release-scope inventory, validation evidence, reviewer-gate status, changelog/version notes, and correct `Closes`/`Refs` issue links. If PR mutation is unavailable, prepare the exact PR body and record the missing credential or command failure.
6. Run the named validation feedback loop required for the release candidate. Prefer repository quality gates such as tests, typecheck, build, generated-mirror checks, changelog checks, and release dry-runs when available. Record skipped checks and residual risk.
7. Run a canonical `reviewer` gate before merge unless the user explicitly skipped it. Address in-scope blockers; record non-blocking findings and out-of-scope follow-ups without starting adjacent issues.
8. Update Keep a Changelog-style notes for the shipped changes. Keep entries factual, grouped by Added/Changed/Deprecated/Removed/Fixed/Security where the repository uses those headings, and derive PR/release notes from the changelog material instead of inventing a separate story.
9. Decide the version bump from the shipped changes and state the rationale. Consider public API changes, user-visible workflow/agent behavior, bug fixes, documentation-only changes, prerelease status, and repository policy. Update version-bearing files only when the release scope calls for it.
10. Re-run or confirm the validation feedback loop after changelog/version changes. Do not merge while generated mirrors, manifests, tests, or release notes are stale.
11. Merge the PR when review, validation, changelog, and version gates pass. Prefer squash merge for issue-sized slices unless repository convention requires otherwise. Record the merge method, PR number, merge commit or squash commit, and any branch cleanup.
12. Create the tag and GitHub Release from the merged release state when the version decision requires a release and credentials/policy allow it. Derive release notes from the Keep a Changelog-style notes, include solved issue links, and record the tag, release URL, and command evidence. If release creation is deferred, record the exact deferred action and reason.
13. Verify post-merge issue and project status. Confirm each fully solved linked issue is closed and Done where possible. Repair obvious automation gaps when credentials and scope allow; otherwise report the issue number, expected state, actual state, attempted command, and missing permission or automation gap.
14. Finalize with the PR, merge method, changelog/release notes, version bump rationale, tag/release result, linked issue/project verification, validation evidence, reviewer-gate result, skipped checks, unrelated-change handling, and follow-up risks.
