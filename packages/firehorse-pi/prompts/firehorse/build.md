# Build

## Purpose

Use this workflow to implement one Agent-Ready Published Issue or issue-sized Vertical Slice by default. It accepts an Issue Draft, Published Issue, or scoped implementation request, confirms the scope before implementation, moves the scoped Published Issue to In Progress with `gh` when applicable, coordinates bounded implementation through the canonical `worker` role when available, applies one-test-at-a-time TDD when feasible, runs a canonical `reviewer` gate for non-trivial changes, verifies against the applicable Verification Contract and acceptance criteria, and records implementation evidence before completion updates.

## Usage

Invoke the generated provider command as `horse-build` with an Issue Draft path, Published Issue URL, Planning Workspace issue reference, or concise vertical-slice description. whole-PRD builds require explicit user request; otherwise treat the requested work as one issue-sized Vertical Slice.

## Inputs

- `$ARGUMENTS`: the Issue Draft, Published Issue, issue URL, file path, or scoped implementation request supplied by the user.
- The applicable Verification Contract, acceptance criteria, dependencies, and non-goals.
- Relevant Planning Workspace artifacts such as PRD Draft, Planning Decisions, issue drafts, prior reviews, and implementation evidence.
- Repository files, tests, docs, package manifests, and project guidance needed to understand the affected code path.

## Outputs

- A scoped implementation for one Agent-Ready Published Issue or issue-sized Vertical Slice unless the user explicitly requested a whole-PRD build.
- The scoped Published Issue moved to In Progress with `gh` after scope confirmation, when a Published Issue is in scope and GitHub access is available.
- Tests, regression checks, or a named alternate feedback loop with rationale when behavior-level automated tests are not feasible.
- Local implementation evidence before completion or Done updates: commands run, observed results, files changed, generated artifacts refreshed, skipped checks, reviewer findings, and residual risks.
- A final implementation summary tied back to the Verification Contract, issue acceptance criteria, TDD contract, review gate, and completion decision.
- Optional concise tracker-update text or comment body after local evidence and any required review gate have been recorded.

## Orchestration Intent

Keep the canonical workflow parent-led and provider-neutral. The build parent owns scope confirmation, issue status movement, TDD contract, implementation evidence, review gate, and completion decisions. First understand the issue and the code path, then move the scoped Published Issue to In Progress with `gh` when applicable, then delegate bounded implementation cycles to `worker` when provider-native subagents are available, then validate, review non-trivial changes with `reviewer`, record evidence, and only then prepare completion updates. The canonical workflow remains a single issue-sized build contract rather than an autonomous delivery graph.

## Safety Gates

- Default to one issue-sized Vertical Slice. whole-PRD builds require explicit user request.
- Do not start broad implementation until the relevant issue, acceptance criteria, Verification Contract, dependencies, and non-goals are understood and the scope is confirmed.
- After scope confirmation for a Published Issue, move only that scoped issue to In Progress using `gh` before implementation; do not move parent PRDs or adjacent issues as part of this workflow.
- Keep parent ownership of the scope, TDD contract, implementation evidence, review gate, tracker completion, and any scope expansion. A delegated `worker` implements only the bounded task it receives.
- Do not skip codebase exploration; inspect the affected area before editing.
- Use one-test-at-a-time TDD when feasible: write or identify one behavior-focused failing check, confirm red, implement the minimal change, confirm green, then refactor only while green.
- If behavior-level automated tests are infeasible or disproportionate, name the alternate feedback loop, explain the rationale, and record the residual risk before implementation proceeds.
- Run a `reviewer` gate for non-trivial code, workflow, generated artifact, release, or architecture-impacting changes before completion.
- Do not invent passing evidence. If validation cannot run, record why and what risk remains.
- Do not post completion comments, close a Published Issue, or move it to Done before local implementation evidence and any required reviewer gate have been recorded.
- Do not add a Firehorse runtime, prompt loader, provider transport, slash-command runtime, hook, or autonomous execution engine.

## Procedure

1. Read `$ARGUMENTS` and identify whether the target is an Issue Draft, Published Issue, Planning Workspace issue, or freeform vertical-slice request.
2. Confirm the work is one issue-sized Vertical Slice. If the user asks for a whole PRD or multi-issue batch, call out the expanded scope and require explicit confirmation before proceeding.
3. Read the Verification Contract and acceptance criteria. Identify expected behaviors, required artifacts, acceptance checks, dependencies, and non-goals. State the parent-owned TDD contract: the behavior to prove, the first failing check to seek, and the evidence needed for completion.
4. If the target is a Published Issue and GitHub access is available, use `gh` after scope confirmation to move only the scoped issue to In Progress. If the status cannot be moved, record the command attempted or the missing credential instead of silently continuing as if it succeeded.
5. Explore the codebase area before editing: relevant modules, tests, generated artifacts, docs, and provider/distribution boundaries.
6. Establish the feedback loop. Prefer a behavior-level automated test and use one-test-at-a-time red/green/refactor. If behavior-level automated tests are infeasible or disproportionate, name the alternate feedback loop, explain why it is sufficient for this slice, and identify the residual risk.
7. Delegate bounded implementation cycles to canonical `worker` when provider-native subagents are available; otherwise perform the same bounded implementation steps directly. The parent workflow retains ownership of scope, TDD contract, implementation evidence, review gate, and completion.
8. Make the smallest scoped code, docs, definition, or generated-artifact changes needed for the vertical slice. Refresh generated mirrors/manifests when canonical definitions changed.
9. Run the feedback loop and any cheap adjacent checks. Capture commands, results, files changed, generated artifacts refreshed, skipped checks, and remaining risks as implementation evidence.
10. For non-trivial changes, run a canonical `reviewer` gate before completion. Address in-scope blockers; record non-blocking findings and out-of-scope follow-ups without starting adjacent issues.
11. If a Published Issue completion update is appropriate, prepare a concise tracker comment from the recorded evidence and reviewer result rather than replacing the evidence.
12. Finalize with the implemented behavior, Verification Contract coverage, acceptance criteria status, TDD or alternate feedback-loop evidence, reviewer-gate result, changed files, and follow-up risks.
