# Create Plan

## Purpose

Use this workflow to convert an ambiguous user ask, issue, PRD seed, or project goal into a durable plan that another agent can safely review and implement. The workflow owns the Planning Workspace artifact contract: preserve the original ask, gathered context, memory findings even when empty, durable research and scouting artifacts, Planning Decisions, a PRD Draft, optional plan-review output, Issue Drafts, publication evidence, and later review artifacts.

## Usage

Invoke the generated provider command as `horse-create-plan` with the ask, issue URL, PRD seed, project goal, or Planning Workspace path. In generated prompt templates and commands, the user's freeform input is available as `$ARGUMENTS`.

Use this workflow when the next useful step is not implementation yet: the request needs context gathering, user decisions, PRD shaping, issue slicing, or publication. If the user already points to one Agent-Ready Issue, prefer `build`. If the user asks only for adversarial review of an existing plan, prefer `plan-review`.

## Inputs

- `$ARGUMENTS`: the user's ask, existing issue URL, PRD seed, Planning Workspace path, or project goal.
- Existing project guidance such as `AGENTS.md`, `CONTEXT.md`, `docs/PROJECT.md`, project-wide `docs/DECISIONS.md`, architecture/codebase docs, PRD workspaces under `docs/prds/`, and relevant package manifests.
- Memory or prior-session findings from available memory tools, recorded even when the result is empty.
- Research and scouting evidence from local code inspection, issue tracker inspection, and optional web or documentation research.
- User answers to batched grilling questions and any explicit non-goals, constraints, publication preferences, or sequencing decisions.

## Outputs

- A Planning Workspace under the project's durable planning location, normally `docs/prds/prd-000N-<slug>/`, following the next available sequence number plus a human-readable slug unless the project has a more specific convention.
- The Planning Workspace artifact contract preserved as named files and directories: `ASK.md` for the original ask; `context/` for gathered context, memory findings, and durable research and scouting artifacts; local `DECISIONS.md` for Planning Decisions; `PRD.md` for the PRD Draft and Verification Contract; optional `PLAN_REVIEW.md`; and later `issues/`, `reviews/`, and publication-log entries.
- A PRD Draft that states the user problem, target outcome, scope, non-goals, risks, dependencies, acceptance checks, and Verification Contract.
- Issue Drafts from the PRD Draft, sliced into dependency-ordered, independently grabbable work items with clear validation evidence.
- Optional Published Issues when the user asks to publish: publish the parent Published Issue before child Published Issues, preserve dependency relationships, and record issue URLs in the Planning Workspace.
- A final status report with artifact paths, unresolved decisions, review recommendation, publication status, Codebase Map gaps, Tracker Project gaps, and next recommended workflow.

## Supporting Capabilities

- Firehorse skill reference: `verification-contract` for converting the plan into expected behaviors, required artifacts, acceptance checks, and dependencies.
- Agent role reference: `plan-reviewer` for the recommended review gate before issue breakdown or publication.
- Upstream skill references: `mattpocock-skills:grill-with-docs` for batched questioning against domain docs, `mattpocock-skills:to-prd` for PRD shaping, and `mattpocock-skills:to-issues` for issue slicing. Treat these as supporting methods only; the canonical Planning Workspace remains the source of truth.
- Required capabilities: file reading and writing so the workflow can preserve durable artifacts.
- Optional capabilities: GitHub issue publication, Tracker Project inspection, local command inspection, provider-native subagents, and web or documentation research when needed.

## Orchestration Intent

Keep the canonical workflow provider-neutral. The parent agent owns the Planning Workspace and decides when enough context exists to draft the PRD, ask the user questions, review the plan, create Issue Drafts, or publish issues. Provider-native subagents may gather independent research, scout the codebase, or review the plan, but their findings must be written back into durable workspace artifacts rather than living only in chat context.

Prefer parallel gathering only for independent questions. Use the workflow to batch independent grilling questions so the user can answer once, then write Planning Decisions to the Planning Workspace's local `DECISIONS.md` as they are resolved. Promote only cross-PRD or repository-wide policy choices to root `docs/DECISIONS.md`; promote durable codebase-facing architecture, logic, convention, testing, integration, concern, or ADR guidance to `docs/codebase/`. Recommend `plan-review` before issue breakdown, publication, or implementation unless the plan is small and high-confidence.

## Safety Gates

- Do not skip the Planning Workspace for non-trivial work; chat-only plans are not durable enough for handoff.
- Do not proceed from ambiguous requirements to Issue Drafts until the unresolved questions are either answered, explicitly deferred, or recorded as Planning Decisions.
- Do not publish issues unless the user asks for publication or the invocation context clearly authorizes it.
- When publishing, publish the parent Published Issue before child Published Issues and record every URL, dependency, and publication failure in the Planning Workspace.
- Do not mark child issues Ready unless they are Agent-Ready Issues with clear scope, Verification Contract, dependencies, and enough repository access for `build` to start without more product clarification; otherwise keep them Backlog.
- Do not overwrite hand-written PRD or issue artifacts without preserving prior content or asking for confirmation.
- Do not create or refresh `docs/codebase/` Codebase Maps inside this workflow; record missing or stale maps as Planning Workspace gaps for a dedicated codebase-mapping workflow.
- Do not append every grilling answer to root `docs/DECISIONS.md`; use the Planning Workspace decision log by default and promote only when the decision's scope warrants it.
- Do not add a Firehorse runtime, prompt loader, provider transport, slash-command runtime, hook, or autonomous execution engine.

## Procedure

1. Identify the planning target from `$ARGUMENTS`: a new ask, existing issue, PRD seed, or Planning Workspace continuation.
2. Create or reuse the Planning Workspace in the durable project location, normally `docs/prds/prd-000N-<slug>/`. Include an index or equivalent map of artifact paths for `ASK.md`, `context/`, `DECISIONS.md`, `PRD.md`, optional `PLAN_REVIEW.md`, `issues/`, `reviews/`, publication log entries, and later review artifacts.
3. Preserve the original ask verbatim before transforming it. Link any source issue, discussion, file, branch, or user-provided artifact.
4. Gather context from project guidance, domain docs, architecture docs, prior PRDs, package manifests, and relevant code. Write gathered context to the workspace with file paths and evidence, not just summaries in chat.
5. Inspect whether relevant `docs/codebase/` Codebase Maps exist and appear fresh enough for the plan. Record missing or stale Codebase Maps as gaps in the Planning Workspace, but do not create or refresh them in `create-plan`.
6. Search available memory for related prior work. Record memory findings even when empty, including the query, result count, date, and any observation IDs or links used.
7. Run targeted research and codebase scouting only as needed. Write durable research and scouting artifacts into the Planning Workspace, including negative findings, assumptions, and source references.
8. Identify independent unknowns. Batch independent grilling questions for the user instead of asking one-by-one, and separate blockers from nice-to-have clarifications.
9. As answers arrive, write Planning Decisions to the Planning Workspace's local `DECISIONS.md` as they are resolved. Each decision should include the question, selected answer, rationale or trade-off, date, downstream effect, and whether it is local-only, promoted to a project-wide decision, or promoted to codebase docs.
10. Draft the PRD using the original ask, gathered context, memory findings, research, Planning Decisions, and Verification Contract. Keep non-goals and dependencies explicit.
11. Recommend `plan-review` before issue breakdown unless the plan is small and high-confidence. If review runs, preserve findings and required changes in the Planning Workspace before continuing.
12. Prepare Issue Drafts from the PRD Draft. Slice them vertically, order dependencies, include expected behavior, validation evidence, affected artifacts, Tracker Status recommendation, and whether each draft is an Agent-Ready Issue.
13. If publication is requested, publish the parent Published Issue before child Published Issues. Link children to the parent, preserve dependency relationships, add issues to the Tracker Project when available, choose Backlog or Ready based on readiness, and record any automation gaps instead of pretending they succeeded.
14. Review the local Planning Decisions for promotion candidates. Append a root Project Decision only for cross-PRD or repository-wide policy changes, and update `docs/codebase/` only for durable codebase-facing guidance.
15. Finalize with artifact paths, issue URLs if any, unresolved decisions, promotion actions taken or deferred, Codebase Map gaps, review status, validation performed, and next recommended workflow such as `plan-review`, `build`, or `review-code`.
