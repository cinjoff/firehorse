## 1. Overall verdict

**Not all addressed.** The branch implements the core Definition Format, parser/validator, projection generator, generated mirrors/manifests, docs, and write/check scripts, and the independently re-run validation passed:

- `pnpm definitions:check` -> `definitions:check validated 3 definitions, 6 generated mirrors, and manifests.`
- `pnpm typecheck` -> passed for `firehorse-core`, `firehorse-pi`, and `firehorse-claude`.
- `pnpm test` -> `2 passed (2)`, `15 passed (15)`.

The main remaining blocker is acceptance-test coverage, not an obvious missing implementation path. Issue #4 explicitly requires tests for invalid frontmatter, and issue #2's PRD/testing decisions call for schema-version, allowed-field, alias/deprecation, malformed-frontmatter, path/ID, upstream-reference, and projection-shape/source-hash coverage. Current tests cover some of this, but not all.

## 3. Blocking gaps before claiming all open issues complete

1. **Complete issue #4 parser/validator test acceptance.** Add explicit tests for invalid/malformed frontmatter, schema-version rejection, unknown frontmatter fields, alias/deprecation handling, ID/path mismatch, wrong-kind references, and unknown upstream references. The implementation appears to enforce most of these through Zod and set validation, but the acceptance criteria require tests.
2. **Complete issue #5 projection test acceptance.** Add assertions that feedback-loop generated skill mirrors preserve the intended instruction content and that source hashes are derived from the canonical source content, not merely shaped like a hash.
3. **Complete issue #7 projection test acceptance.** Add assertions for diagnostic-reviewer role metadata validation plus Claude/Pi provider frontmatter adaptation/filtering and Pi sync-artifact shape.

## 4. Optional follow-ups

- Clarify whether the parent issue #2 phrase "generated mirrors use the `horse-<id>` native name convention" applies to skills. Current implementation and later docs/decisions use `skills/firehorse/<id>/SKILL.md` with `name: <id>` for skills, while workflows and agent roles use `horse-<id>`. This appears intentional from D-104 and the docs, but the parent wording can be read more broadly.
- Current implementation is substantially complete functionally; the remaining blockers are primarily acceptance-test/documented-evidence gaps rather than observed runtime failures.
