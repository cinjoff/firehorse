# PRD-0006 Decisions

1. Firehorse should fully stop exposing upstream `pi-agent-memory` once the Firehorse Pi claude-mem wrapper is implemented. Remove upstream `pi-agent-memory` from Firehorse Pi manifests and dependency/bundling lists if no Firehorse code imports it; evaluate `claude-mem` bundling separately based on whether Firehorse imports worker scripts. Rationale: keeping both wrappers active risks duplicate session lifecycle handling, double observation capture, and conflicting project identity behavior.
2. Firehorse Pi memory tools should use the short `mem_` prefix: `mem_search`, `mem_timeline`, and `mem_get_observations`. Rationale: generic MCP names (`search`, `timeline`, `get_observations`) are too ambiguous in Pi's global tool namespace, while longer `claude_mem_` names are unnecessarily verbose.
3. Firehorse should not keep `memory_recall` as a compatibility alias. Rationale: `memory_recall` encourages one-shot recall and preserves the rigidity this wrapper replaces; Firehorse skills/workflows should use the progressive `mem_search` → `mem_timeline` → `mem_get_observations` pattern.
4. Firehorse should capture Pi session observations by default, and automatic context injection should also be enabled by default but capped to 20 observations. Rationale: useful project-scoped context should be available by default once Firehorse resolves the correct memory project identity; progressive `mem_` discovery remains the path for deeper recall.
5. The Firehorse memory wrapper should discover and report the existing claude-mem worker; Firehorse should not auto-start or manage a bundled worker in v1. Rationale: the wrapper should not silently assume ownership of worker lifecycle or database startup.
6. Captured Pi observations should use `platformSource: "firehorse-pi"`. Rationale: cross-engine search is project-scoped, while `firehorse-pi` gives clearer provenance than upstream `pi-agent`.
7. Firehorse Setup Manifest identity should win over environment variables when present. Existing env values are fallback unless an explicit override such as `FIREHORSE_MEMORY_PROJECT_OVERRIDE=1` is set. Rationale: checked-in project setup should prevent launcher/global env drift.
8. Cross-project memory search should be allowed only through an explicit `project` parameter on `mem_search` and `mem_timeline`; default behavior stays scoped to the resolved Firehorse project. Rationale: deliberate cross-project lookup is useful, but accidental memory bleed must be hard to trigger.
9. Firehorse should treat ArtemisAI `pi-mem.ts` as a behavioral reference, not copied source. Reimplement the wrapper in Firehorse style from claude-mem HTTP contracts and Pi extension docs, and document provenance in PRD/third-party notices as needed. Rationale: Firehorse is MIT while upstream `pi-agent-memory` is AGPL-licensed.
10. Observation capture privacy in v1 should rely on claude-mem's prompt/session filtering plus Firehorse-side memory-tool skip rules and response truncation. Rationale: extra semantic filtering is a separate product risk and should not block a thin wrapper.
11. Firehorse wrapper output, injected context, status text, and skills must not advertise stale upstream names such as `get_observations([IDs])`, `mem-search skill`, or `memory_recall`; guidance must say `mem_search` → `mem_timeline` → `mem_get_observations`. Rationale: injected guidance drives agent tool choice.
12. The Pi status command should be `/mem-status`. Rationale: it matches the `mem_` tool prefix and avoids stale `/memory-status` or longer `/claude_mem_status` naming.
13. Automatic context injection should be controlled by `FIREHORSE_MEM_INJECT=0|1`, `FIREHORSE_MEM_INJECT_MAX_OBSERVATIONS`, and `FIREHORSE_MEM_INJECT_MAX_TOKENS`; default is enabled with a 20-observation cap. Rationale: explicit controls preserve context budget while keeping useful scoped memory available by default.
14. The primary Firehorse Pi memory extension should be `firehorse-mem.ts`. Fold project resolution from `firehorse-memory-project.ts` into it, retire `firehorse-memory-project.ts`, and retire `firehorse-claude-mem-worker.ts` in v1. Rationale: one wrapper should own memory project/tool/lifecycle behavior, while worker startup should be an external claude-mem setup concern.
15. Injected memory context should use `<firehorse-mem-context>` rather than `<pi-mem-context>`. Rationale: Firehorse owns this wrapper surface and should not advertise upstream adapter names.
16. Memory capture should be on by default with `FIREHORSE_MEM_CAPTURE=0` as the opt-out. Rationale: Pi sessions should contribute observations unless explicitly disabled.
17. `mem_get_observations` should not runtime-enforce that `mem_search` happened earlier. Rationale: IDs may come from pasted context, timelines, or user-provided references; tool descriptions and skills should enforce the progressive workflow socially.
18. Firehorse should preserve claude-mem worker output mostly raw, adding only wrapper error messages, project/default metadata, and output caps. Rationale: claude-mem already formats useful search/timeline/detail output, and unnecessary transformation risks losing context.
19. Firehorse should rewrite/wrap claude-mem injected-context headers and footers with Firehorse-owned guidance. Rationale: upstream injected context currently advertises stale tool names such as `get_observations([IDs])`, `mem-search skill`, and `memory_recall`; Firehorse must advertise only `mem_` tools.
20. Firehorse should not filter stale observation content in v1. Rationale: memory observations are historical records; the wrapper should preserve them and tell agents that memory may be stale and must be verified against live files/docs.
21. Injected context should include a clearly marked IMPORTANT 3-layer workflow, not only a minimal hint: `mem_search` for compact IDs, `mem_timeline` for surrounding context, then `mem_get_observations` for selected full details. Rationale: claude-mem's own docs emphasize this workflow to prevent context blowups.
22. Stale memory observations and stale injected instructions should become Session Audit or future memory-quality findings, not wrapper-side mutations of stored memory. Rationale: quality analysis belongs in assessment workflows, while this wrapper should stay thin and non-destructive.
23. Firehorse should expose raw worker-context debugging as a user command such as `/mem-status --raw-context` or future `/mem-debug`, not as a model tool. Rationale: raw context is useful for diagnosis but should not encourage agents to bypass progressive discovery.
24. Firehorse should use `/api/health` as the canonical claude-mem worker health endpoint. Rationale: claude-mem's OpenClaw integration docs describe `/claude_mem_status` as checking worker health, and the corresponding integration source calls `/api/health`; no official evidence currently supports `/health` as the primary endpoint.
25. Firehorse should mirror claude-mem MCP parameter names exactly for progressive tools: `obs_type`, `dateStart`, `dateEnd`, `orderBy`, `depth_before`, `depth_after`, and `ids`. Rationale: preserving upstream names reduces friction when translating docs, memories, and MCP examples into Pi.
26. Firehorse should cap memory tool output with `FIREHORSE_MEM_TOOL_MAX_CHARS`, defaulting to a generous but bounded value while preserving worker formatting up to the cap. Rationale: memory tools can return large prior context and must not flood Pi sessions.
27. Firehorse should replace upstream `mem-search` with a Firehorse-owned skill named `mem`. Rationale: the new guidance covers capture, search, timeline, observation fetch, project scoping, and staleness—not only search.
28. Firehorse should not expose server-beta write/generation tools such as `observation_add`, `observation_record_event`, or generation/status tools in v1. Rationale: v1 is a worker-mode recall/capture wrapper, not a manual memory mutation surface.
29. Automatic context injection should be enabled by default but capped to 20 observations, superseding earlier default-off/tiny-cap wording. Keep `FIREHORSE_MEM_INJECT=0` as the opt-out and add an observation-count cap such as `FIREHORSE_MEM_INJECT_MAX_OBSERVATIONS` defaulting to `20`. Rationale: useful project-scoped context should be available by default once Firehorse resolves the correct memory project identity.
30. `mem_search` should default `limit` to `20`, matching claude-mem's compact-index workflow. Rationale: the first layer should provide enough IDs to filter without loading full details.
31. `mem_get_observations` should cap batched fetches to 10 IDs by default. Rationale: full observation details are intentionally the expensive third layer and should not flood context accidentally.
32. `/mem-status` should show last injection project, observation count, and size/limit metadata, but never dump raw injected context unless the user passes `--raw-context`. Rationale: status should make context cost visible while keeping raw memory out of normal command output.
33. Delete `firehorse-memory-project.ts` in the same implementation slice once `firehorse-mem.ts` owns project resolution. Rationale: a separate project-only memory extension would duplicate resolution order and increase load-order risk.
34. Retire `firehorse-claude-mem-worker.ts` rather than keeping it as a separate auto-start helper. The Firehorse wrapper should rely on an already installed/running claude-mem worker and report setup gaps through `/mem-status` and setup docs. Rationale: the user wants a thin wrapper over an existing claude-mem worker; auto-starting a bundled worker creates ownership ambiguity and hides setup state.
35. Remove `pi-agent-memory` from root workspace dependencies, `packages/firehorse-pi` dependencies/bundled dependencies, Pi manifests, lockfile, and notices if no Firehorse code imports it. Rationale: Firehorse should stop relying on the upstream adapter entirely.
36. After a final PRD consistency pass, create implementation issues from this PRD. Rationale: the resolved scope is large enough to split into independently grabbable implementation slices.
37. When the claude-mem worker is missing, `/mem-status` and setup docs should report that the worker is not reachable and tell the user to install/start claude-mem; Firehorse should not auto-install or auto-start it. Rationale: worker ownership belongs to claude-mem, not the Firehorse wrapper.
38. Remove `claude-mem` bundling unless implementation proves Firehorse imports worker scripts. If the wrapper only talks to an existing worker, prefer setup documentation over bundled scripts. Rationale: without auto-start, the dependency is likely docs/setup-only and bundling creates ownership ambiguity.
39. Release notes must explicitly announce that `memory_recall` is removed and the replacement is `mem_search` → `mem_timeline` → `mem_get_observations`. Rationale: this is a breaking user/tooling migration.
40. Implementation issue slices should cover helper/project/worker discovery, `firehorse-mem.ts` progressive tools, lifecycle capture/injection, package/dependency cleanup, `mem` skill/setup docs, tests/smoke validation, and a Session Audit memory-quality follow-up if needed. Rationale: these are independently grabbable vertical slices.
41. Mark the PRD status as `Draft — grilled, ready for issue breakdown` after consistency pass. Rationale: the design decisions are resolved enough to turn into implementation tickets.
42. Publish the approved PRD-0006 issue set to GitHub Issues #26-#32 and update local draft files with published issue links. Rationale: implementation work should now be tracked canonically in GitHub while the Planning Workspace preserves the design context.
