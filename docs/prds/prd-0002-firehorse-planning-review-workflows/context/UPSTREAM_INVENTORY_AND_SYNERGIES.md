## Architecture

Firehorse currently has no shared skill runtime. It ships static provider-native surfaces:

- **Core** owns canonical definitions and upstream provenance (`packages/firehorse-core/definitions`, `packages/firehorse-core/upstreams`).
- **Pi distribution** exposes resources via `package.json#pi`, bundles selected npm packages, and adds Pi-only extensions for setup, memory worker lifecycle, Superset env loading, update checks, and subagent defaults.
- **Claude distribution** exposes the same local skills as a Claude plugin, mirrors shared pi-subagent agents, depends on upstream `claude-mem`, and adds a startup update-check hook.
- **Upstream skills/tools** remain owned by their packages/repos. Firehorse mirrors or re-exports them with pinned provenance rather than merging runtimes.

## Synergy clusters

1. **Bug diagnosis and fix loop**: `horse-fix-bug` + Matt `diagnose` + Firehorse `feedback-loop` + `verification-contract` + pi-lens AST/LSP tools + context-mode sandboxing + `memory_recall` + current reviewer/code-reviewer role support for final review.
2. **Upstream/package maintenance**: `horse-update-upstreams` + upstream `UPSTREAM.json` manifests + `librarian`/pi-web-access for evidence + context-mode for large checks/logs + pi-lens for code validation + reviewer/code-reviewer role support for provenance and generated-file freshness.
3. **UI implementation/design**: `shadcn` for component/registry correctness + `impeccable` for UX/design quality + Matt `prototype`/`tdd` + pi-mermaid for diagrams + pi-web-access/librarian for external docs/examples.
4. **Planning to tracked work**: `grill-with-docs`/`grill-me` + `to-prd` + `to-issues` + `triage` + shared `context-builder`/`planner`/`oracle` agents.
5. **Multi-agent execution**: pi-subagents `subagent` tool and `/run`/`/chain`/`/parallel` commands + Firehorse subagent defaults granting web/LSP/memory/context tools + Claude mirrored agents for comparable roles.
6. **Context and memory continuity**: context-mode handles large transient data; pi-agent-memory/claude-mem handles cross-session recall; Firehorse memory-project extension keeps Superset/Conductor worktrees mapped to canonical project identity.
7. **External integrations**: `firehorse-setup` + `pi-mcp-adapter` + `firehorse-superset-env` enable user-global Superset MCP/API access; pi-web-access covers general web/GitHub/video research.

## Gaps, conflicts, duplication

- **Intentional duplication / drift risk**: Pi and Claude skill trees are mirrored with identical file sets (114 files each, 18 SKILL.md entrypoints). This is expected static projection, but any manual edit would risk drift; generated Firehorse files say to edit canonical definitions instead.
- **Pi agent discovery gap**: `firehorse-pi` includes generated Firehorse agent files, but package agent directories are not discovered by `pi-subagents` at runtime; projection notes say `firehorse-setup` can copy Pi-compatible sync artifacts into the user's Pi agent directory.
- **Worker does not get shadcn by default**: `firehorse.subagents.json` explicitly says shadcn is exposed but not granted to worker by default yet, so UI tasks may require explicit skill attachment.
- **Context-mode surface is partial in Pi manifest/commands**: Firehorse exposes context-mode skills `context-mode`, `ctx-doctor`, `ctx-insight`, `ctx-stats`; context-mode package also contains `ctx-purge`/`ctx-upgrade` skills and documents more meta-tools. Pi extension visibly registers only `/ctx-stats` and `/ctx-doctor` commands.
- **License mix to track**: `pi-agent-memory` is AGPL-3.0 while many other bundled/mirrored resources are MIT/Apache-2.0. Inventory only; release/legal handling should stay explicit in notices.
- **Network-on-startup behavior**: Pi `firehorse-update-check.ts` and Claude `check-update.mjs` perform cached/timeout-bounded release checks on startup. This is distribution-extension behavior, not core detection, but operators may need skip/env controls in restricted environments.
- **Two memory owners**: Claude gets upstream `claude-mem` as a plugin dependency; Pi bundles `claude-mem` scripts and starts worker for `pi-agent-memory`. This is by policy, but versions/SHA/package pins must stay synchronized.
- **Overlapping research/fetch tools**: context-mode fetch/index and pi-web-access fetch/search both retrieve external content. They serve different roles (context-minimizing FTS vs web/GitHub/video research), but agent guidance should choose deliberately.

## Remaining clarification questions

2. Should any default subagent (especially `worker`) receive `shadcn` and/or `impeccable` skills for UI work, or should UI skills remain opt-in?
3. Is npm package version enough provenance for `pi-subagents`, or should its `UPSTREAM.json` also pin a git ref/commit like the other upstreams?
4. Should Firehorse document/update-check skip env vars centrally for air-gapped or no-network startup environments?
5. For Pi users, is `firehorse-setup` the intended required step for installing generated Firehorse agents into the runtime-discovered agent directory?
